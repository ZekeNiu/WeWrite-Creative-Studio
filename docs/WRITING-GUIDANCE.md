# 公众号创作规则的维护

工作台在完整加载固定版本 WeWrite 技能后，追加应用层的创作约定。规则服务于文章的主线、内容完整性、账号声音和阅读节奏。事实核查仍负责判断来源支持什么；编辑根据这些判断写准原句，避免用泛泛的免责说明打断论述。

## 单一维护入口

`backend/writing_guidance.py` 提供 `instructions(purpose)` 和 `metadata(purpose)`。原生执行入口与兼容提示入口读取同一份内容，不在每个入口复制编辑规则。修改规则时递增 `VERSION`；元数据同时记录实际规则的 SHA-256，便于区分使用同一版本号但内容不同的运行。

| 任务目的 | 规则作用 |
| --- | --- |
| sources | 整理可写主张；具体条件保留在 boundary，工作提醒留在任务记录 |
| outline | 按论述推进安排章节；约束与面向读者的要点分开 |
| write | 写成完整文章，保护段落承接、观点和表达 |
| review / edit | 针对正文已有问题修改；改句后复查上下文与作者声音 |
| revise | 遵守选段范围和本次修改要求 |
| rewrite | 在目标平台保留原稿内容、具体条件和声音 |

`fact_audit`、研究、选题、配图、学习等任务不注入这些创作规则。兼容编辑器依据结果类型选择任务目的：`FactAudit` 使用 `fact_audit`，`EditedDraft` 使用 `edit`。模型服务仍由原来的 route 选择；不要再次把“使用审稿模型”与“正在编辑文章”混为一谈。

运行任务的 `writing_guidance` 为可选诊断字段；成功原生执行的记录也携带该字段。旧记录没有此字段时保持原样，不推断它采用了当前规则。文章字段、公开操作接口和数据库结构不需要迁移。

## 内容与约束的交接

主张的事实、状态、来源编号及具体适用条件继续进入写作上下文。内部核查过程不投影成文章主张。任务书中的约束指导写作，章节的 title、purpose、points 用于安排读者会读到的内容。旧大纲中混入的作者提醒由模型按指导信息理解，程序不按词表删除历史文本。

本篇明确要求、确认过的立意、选段范围、人工修改和账号声音仍是输入。规则不引入自动重写历史文章、额外审稿轮次或词语禁用表。必要条件与反方可以成为文章的重要内容；类比和第一人称判断不自动等同于事实断言或作者亲历。

## 验证方法

自动化回归覆盖实际提示入口、任务目的与模型路由的分离、版本记录、完整上游加载、主张条件保留、来源排除、人工冲突和候选采用。`tests/fixtures/narrative_cases.json` 给出五组成对编辑案例，作为真实成稿复查的参考；示例文字不是必须逐字匹配的模型答案。

`tools/draft_quality_benchmark.py` 默认使用 `--engine native`，两个 variant 都通过生产的 `workflow.run` 执行大纲、初稿、审稿；variant 只标识对照身份。旧流程仅由显式 `--engine legacy` 启用，不用它证明原生流程的效果。

对照输入为冻结的本地快照：`--settings-root` 下的 `data/studio.sqlite` 提供同一模型配置与账号上下文；`--bundle` 的 cases 每项包含 case 名称及 article 输入。工具从快照建立独立数据库，生成新的诊断文章，关闭搜索并禁止补充网络资料。`--code-root` 分别指向冻结基线和候选代码。manifest 记录材料、配置、账号、代码、运行器与上游版本身份。诊断数据、文章、快照和凭证仅留在忽略目录，不提交到仓库。

检查每份结果的 status、review 和阶段记录；程序结束或模型自评通过均不等于写作质量已经验证。复查原题是否回答完整、段落是否顺畅、无信息增量的免责是否减少、表达特色是否保留，以及事实、关键反证与结论强度是否准确。任何模型接口失败单独记录，不归因于写作规则，也不藏在平均分里。
